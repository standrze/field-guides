The answer to the main question

You can use Laguna to teach another model, continue training Laguna itself, or prune Laguna into a smaller derivative and retrain it. A student does not have to be smaller. Only choosing a smaller student or physically reducing the architecture lowers its parameter count.

This guide addresses a specific goal: a local assistant for legitimate defensive cybersecurity work, including configuration review, incident evidence interpretation, secure code review, remediation, and answers grounded in trusted documentation. It is designed around a 64 GB M5 Max Mac and an alternative machine with one RTX 4090 and 128 GB of system RAM.

The destination: a leaner cyber model

The deliverable is a model that handles the intended cybersecurity tasks reliably while using less memory or less time than the current baseline. Same-size fine-tuning can help develop the training data, but it completes the efficiency goal only if it produces a measured operating-cost improvement. A smaller pretrained student or recovered pruned model is the direct route to fewer parameters.

My starting recommendation is a quantized dense Qwen 4–8B student, because it provides a small storage target and the 4B training path has already worked locally. Compare GPT-OSS-20B as the sparse alternative and Laguna as the existing teacher and quality reference. The final choice must pass a quality floor on your tasks; no matched local benchmark yet establishes a winner. See the three-way comparison and the GPT-OSS chapter.

Resolve the names first

The NVIDIA method is Minitron. The Laguna checkpoint inspected for this project is Laguna XS 2.1, published as about 33 billion total parameters and 3 billion active per token. We have not established an official 27B Laguna checkpoint here. When this guide discusses “Laguna 27B,” it is a hypothetical model or derivative. The same principles would apply after verifying that checkpoint’s actual configuration. Laguna model card.

Likewise, “Qwen 4B” describes a size, not a model generation named Qwen4. The existing pilot used Qwen3-4B-Instruct-2507. The architecture comparison later uses the specific dense Qwen3-8B model. Other members of the Qwen family use different architectures, including mixtures of experts.

How to read the evidence

Published finding means a cited research result in its own model, data, and hardware setting. Local measurement means a result from the small Midnight experiment. Planning estimate means arithmetic or a proposed experiment, not a verified capacity or schedule. The guide keeps these separate because a 40-example adapter run and a billion-token pruning-recovery run answer very different questions.

Use the chapters in sequence, or search for a term with the chapter finder. You can also read or print the entire guide on one page. The proposed goal is a reliable specialist, with enough general language and reasoning ability to understand unfamiliar evidence.

A model’s weights are the numerical parameters saved in its checkpoint. They encode distributed patterns learned during training. Activations are the intermediate values produced when those parameters process a particular input. The activations from reading a French sentence and a firewall configuration differ, even though many of the same weights participate.

There is no dependable mapping from “French” to a clean folder of parameters that can be removed while leaving code comprehension unchanged. A circuit useful for one language can also support syntax, names, comparisons, or reasoning in other tasks. Some features or experts specialize statistically, but specialization is not an ownership label for an isolated topic.

Four memory budgets

Memory categoryDuring normal useDuring training
Model weightsUsually resident, or moved through an offloading systemStill needed, even when frozen
Activations and workspaceTemporary forward-pass workMore values retained or recomputed for gradients
Attention KV cacheStores earlier keys and values during generationTraining has its own attention state; do not equate it with the serving cache
Gradients and optimizer stateNormally absentNeeded for the parameters being updated

Turning off unnecessary activation logging can save memory, and activation checkpointing trades extra computation for lower training memory. Neither technique erases a language. At inference, implementations normally discard many intermediate activations already. The more direct way to reduce the stored model is quantization or structural pruning.

A useful storage calculation

Ideal weight bytes = parameter count × bits per parameter ÷ 8

At four bits, 8B parameters need an ideal 4 GB of raw weight data, and 33B need 16.5 GB. Actual checkpoints add quantization scales, some higher-precision tensors, metadata, and possibly separate adapters. Runtime memory adds attention state and work buffers. GB here means decimal gigabytes; GiB is a different unit.

Learning another fact usually changes existing numbers rather than appending a new block of weights. That is why repeated fine-tuning does not make a fixed architecture grow with each example. It also explains why “forgetting” a fact does not automatically reclaim a corresponding number of bytes.

Zero is still a stored number

Unstructured pruning sets individual weights to zero. A normal dense tensor still stores those positions, and an ordinary dense kernel can still perform the same operations. Structured pruning changes tensor dimensions or removes complete modules, making storage savings easier to realize. Sparse formats can exploit zeros, but require compatible storage and kernels; a percentage of zeros is not itself a deployment result.

For this project, report stored weight bytes, peak process and accelerator memory, context size, and end-to-end answer time separately. The training-memory anatomy documentation is a useful reference for why training memory exceeds the saved checkpoint.

Minitron starts with an already trained model. It searches for a smaller architecture within that model, carries over compatible weights, and uses knowledge distillation during continued training. The original family derived roughly 8B and 4B models from a roughly 15B Nemotron parent. This is inherited-weight compression rather than learning language from random initialization. Original Minitron paper.

  1. 1. MeasureRun representative inputs and estimate which structural components matter.
  2. 2. PruneCreate smaller tensors or remove modules, preserving compatible trained weights.
  3. 3. RecoverTrain the student with teacher supervision and evaluate what was lost.

What gets measured?

A calibration pass gathers signals about components such as attention heads, hidden channels, or feed-forward dimensions. Those signals help rank candidates for removal. A component that contributes little on the calibration distribution can be a better pruning candidate than one that carries large useful signals. This is a statistical estimate, not a proof that the component is unnecessary for every future prompt.

A defensive specialization project should calibrate on its intended tasks, while retaining a general-language and code-comprehension slice. If calibration contains only short authentication logs, the selected structure may be poor at reading long policy documents. Calibration coverage is part of the architecture decision.

What changes physically?

Width pruning reduces selected dimensions inside layers; depth pruning removes transformer blocks. Dependent matrices must remain consistent. If a feed-forward intermediate channel disappears, its corresponding input and output connections must be removed together. A hidden-width change has broader consequences because many layers share that residual-stream dimension.

The resulting student has smaller actual tensors. It initially loses some ability because the original network was trained to use the complete structure. Recovery training adjusts the remaining parameters so they can compensate. A parent’s weights provide a strong starting point, but no rule guarantees that any chosen fraction of parameters can be removed successfully.

What does the teacher supply?

During distillation the teacher provides richer targets than a single correct label, often next-token probability distributions. The student is optimized to reproduce relevant behavior. The teacher’s forward pass adds training cost; the deployed student does not require the teacher afterward. The official Minitron repository describes the family and links its pruning and distillation tools.

Why the published savings need context

The original paper reports up to 40 times fewer training tokens for an additional small model compared with its from-scratch comparison. That is different from its approximately 1.8-fold compute saving for an entire model family, including the parent. It is not a claim that a local model becomes 40 times faster.

The later Minitron study used 94B student-recovery tokens for its approximately 4B Llama derivative and 380B for its approximately 8B Mistral NeMo derivative, along with a substantial teacher-correction stage. Its small calibration sample count is not the recovery dataset size. These published successes establish the method; they do not establish that Laguna can recover a 33B-to-8B reduction from a few thousand examples. Minitron pruning and distillation practice paper.

For Midnight

“Minitron-style” should mean actual structural reduction plus recovery and evaluation. An adapter on an already-small Qwen model is a useful distillation experiment, but it does not prune Laguna.

A teacher is the model providing supervision. A student is the model being updated. Those are roles, not necessarily size categories. A large model can teach a smaller model, a same-size model, or another version of itself. The teaching signal and training objective determine what gets transferred.

Answer-based or sequence distillation

Give Laguna a defensive question and relevant evidence. Save its answer, review its claims and recommended actions, and train the student to produce the reviewed answer for that input. The student learns the likelihood of that text token by token. Its tokenizer can differ from Laguna’s because the transfer artifact is text, not a vector whose entries must correspond.

For example, a case could ask whether an application configuration satisfies a stated access policy. The training target would identify the relevant setting, connect it to the supplied policy, distinguish missing evidence from a confirmed issue, and recommend a bounded correction. The quality of those connections matters more than merely producing valid JSON.

This approach permits offline generation: run the teacher, unload it, then train the student. It is the closest match to the existing Midnight experiment. It loses the alternatives contained in the full teacher probability distribution and can reproduce teacher errors if review is weak. Sequence-level knowledge distillation.

Probability-based or logit distillation

Instead of teaching only the selected word, match the teacher’s distribution over possible next tokens. A typical loss combines ordinary supervision with a divergence between the teacher and student distributions. A temperature can soften these distributions so less probable alternatives still contribute to learning. Foundational knowledge-distillation paper.

Training objective ≈ weight A × correct-answer loss + weight B × teacher-distribution loss

This is an explanatory form, not a universal recipe. The coefficients, temperature, token masks, and direction of the divergence must be chosen and validated. Ordinary elementwise matching requires token entries and positions to mean the same thing. Laguna and Qwen vocabularies do not satisfy that condition automatically. NVIDIA’s standard Bridge distillation path explicitly requires a shared tokenizer. Specialized cross-tokenizer alignment is separate engineering. Implementation requirement.

Representation distillation

Another option aligns selected hidden representations. If widths or layer counts differ, the system needs a deliberate mapping, such as chosen layer correspondences or learned projections. A 2,048-dimensional Laguna vector and a 4,096-dimensional Qwen3-8B vector cannot simply be treated as equivalent coordinates. Matching all hidden states also increases memory and storage requirements.

The teacher is not an upper bound on every task

A student can surpass its teacher on a focused task when it also receives stronger human labels, trustworthy new evidence, multiple teachers, or a better task-specific training distribution. Teacher-only imitation does not guarantee that improvement. Distillation transfers useful behavior through examples and objectives; it is not an exact copy of the teacher’s complete knowledge.

Direct answer

If you have a compatible Laguna 27B checkpoint, you can use it as the student. You can also use our inspected 33B Laguna as the student. Distillation does not require a reduction in parameter count.

For same-size distillation, the teacher can be a frozen earlier checkpoint, a stronger external model, an ensemble, or a model supplied with better evidence and more time to construct a reviewed answer. Self-distillation means a model’s own behavior supplies supervision for another mode or checkpoint. It is not automatic self-improvement: copying unverified mistakes can reinforce them.

Can 33B become 8B?

Conceptually, yes, by building or choosing an 8B student and training it. Structurally shrinking 33B to 8B removes about 75.8% of the total parameters. A hypothetical 27B-to-8B reduction removes about 70.4%. Those are aggressive reductions, not established Laguna quality-retention results.

Starting with an already trained 8B student makes the experiment easier because it already understands language and code. Starting with inherited pruned Laguna weights preserves compatible internal features but adds pruning and recovery work. Starting an 8B model from random weights adds the much larger task of learning a foundation model. These choices should not all be described as “a small fine-tune.”

Why same-size distillation may be the right first step

If the main problem is that Laguna gives the wrong kind of answer, lacks your documentation, or handles uncertainty poorly, changing its training targets may address that without structural compression. Keep the model size fixed and measure the specialization benefit first. This separates “can our data improve the task?” from “how much capacity can we remove?”

Same-size distillation does not reduce stored weight bytes at the same precision. It might teach shorter useful answers or better use of evidence, which can improve task latency, but those effects must be measured. Quantization remains a separate storage choice. More examples update a fixed set of trainable parameters; they do not create a new memory module for every fact.

A practical comparison is therefore three checkpoints on the same held-out cases: original Laguna, adapted Laguna, and an adapted smaller pretrained student. Structural pruning becomes a fourth candidate when its implementation and recovery budget are ready.

In a mixture-of-experts model, some feed-forward layers contain many alternative expert networks. A router selects a subset for each token, combines their outputs, and passes the result onward. The experts are numerical transformations, not separate chatbots with names such as “French” or “cybersecurity.” Different tokens in one sentence can use different subsets.

Laguna XS 2.1 has 40 layers, with 10 global-attention layers and 30 sliding-window-attention layers. Its published design has 256 routed experts plus a shared expert in each sparse layer. The configuration selects eight routed experts per token; the shared expert is also used. The first feed-forward layer is dense and the remaining 39 are sparse. Model overview; configuration.

Three different ways to make it smaller

  1. Remove experts. Shrink the expert banks and the router’s choice set. This can reduce stored weights substantially. If each token still uses eight experts of the same width, the main expert computation per token may remain similar.
  2. Reduce expert width or active expert count. Narrower feed-forward networks or fewer selected experts can reduce active computation. They also alter what the network can express and require recovery.
  3. Reduce depth or other dimensions. Fewer blocks can reduce sequential computation and attention state. Attention-width and hidden-width changes introduce additional shape and compatibility constraints.

A worked example: why keeping one quarter is not enough

Consider an illustrative 33B model with 2B parameters outside its routed experts and 31B inside them. This is a teaching example, not an exact Laguna tensor audit. Keep 64 of 256 experts in every sparse layer while preserving their widths:

New total ≈ 2B fixed + 31B × (64 ÷ 256) = 9.75B

To reach 8B in that example, the routed banks would have to retain roughly 19.4% of their original size, or additional parts would have to shrink. The actual architecture should be sized from its tensor shapes, including embeddings, attention, shared experts, routers, and output head. Editing a configuration number alone does not remove the matching tensors correctly.

The router must adapt

Removing experts changes which alternatives a token can choose. Routing frequencies measured before pruning may not describe the best routing after pruning. A rarely selected expert can still be valuable for an unusual but important case. A defensible selection process considers task loss and coverage, then evaluates the recovered model on cases outside the calibration pool.

The student needs consistent expert indices and router outputs, valid top-k settings, and a recovery strategy that can adjust the affected network. An adapter limited to the last few attention projections is not automatically enough to repair a heavily pruned router and expert system. Current ModelOpt guidance supports several MoE pruning dimensions but warns that large reductions are difficult to recover. Its support for other MoE architectures does not prove a working Laguna conversion. Pruning support and limitations.

Smaller storage does not guarantee faster answers

An 8B dense model uses much of its network for every token. A 33B MoE with roughly 3B active can perform less active weight computation while keeping a much larger collection of experts in memory. Kernel efficiency, memory bandwidth, routing overhead, attention, batch size, and answer length determine which is faster on a particular machine.

That is why a realistic target has several measurements: total weight bytes, active computation, peak memory at the intended context, and time to a correct complete answer. It is entirely possible for an 8B dense student to save memory without beating Laguna’s latency.

Which is best here?

For the first compact deliverable, I would start with the existing dense Qwen 4B training path and compare a supported 8B checkpoint if quality is insufficient. GPT-OSS-20B is the next sparse candidate to benchmark. Keep Laguna when its measured task advantage justifies its larger stored model, or use it to teach the smaller candidates. This is an engineering recommendation for this project, not a claim that Qwen has the best underlying intelligence.

What crosses the architecture boundary?

Distilling Laguna into Qwen does not turn Qwen into Laguna. The student retains its own tokenizer, attention layout, hidden dimensions, feed-forward structure, and runtime. It learns to solve the selected tasks using that machinery. Architecture matters differently depending on what is being transferred.

Transfer methodMust the architecture match?Practical consequence
Reviewed answer textNoRetokenize text for the student; use its own chat template and end tokens.

Hidden-state matchingNot necessarily, but correspondence must be designedDifferent widths, layers, or sequence positions need mappings.
Prune and inherit weightsCompatible structure is essentialPreserve or explicitly transform the connected tensor dimensions and model configuration.

A concrete comparison

The specific Qwen3-8B checkpoint is a dense 8.2B model with 36 layers. Its configuration specifies hidden width 4,096 and vocabulary size 151,936. The inspected Laguna configuration has hidden width 2,048 and vocabulary size 100,352, with a different attention and MoE layout. These are architecture facts, not quality rankings.

The larger Qwen vocabulary is not a dictionary of extra facts. Tokenization determines how text is segmented. The same log line, identifier, or source-code fragment may take a different number of tokens in each model. That affects sequence budgets, loss positions, prompt cost, and context use. It also makes raw token-per-second comparisons insufficient on their own: compare the same tasks and complete answers.

Reasons to use a pretrained Qwen student

A supported small dense checkpoint provides an immediate training and deployment baseline. It avoids the need to identify removable Laguna structure. Existing language and code knowledge gives the student a useful starting point; reviewed teacher examples can then target the desired task behavior. The cost is that it may lack some of Laguna’s useful strengths, and a smaller dense student may not be faster than the sparse teacher.

Reasons to keep Laguna’s architecture

You can preserve its tokenizer, some of its internal representations, and its sparse computation design. A modest pruned derivative may retain useful inherited weights. This also makes ordinary same-tokenizer distillation more straightforward. However, custom attention, expert routing, quantization, and runtime assumptions must survive the change.

A same-sized Laguna student is the simplest architecture-preserving experiment: no pruning is required. A smaller Laguna derivative is a different level of work. You must confirm model loading, gradients, checkpoint export, cache behavior, and actual inference performance for the modified configuration.

Keep the comparison fair

Give all candidates the same task definitions, evidence quality, source-family splits, and evaluation rubric. Let each use its correct tokenizer and chat formatting. Measure enough context for the task rather than requiring identical token counts. Include each unchanged student so improvements from distillation are distinguishable from the abilities it already had.

A comparison of Qwen, Laguna, and GPT-OSS checkpoints combines architecture, pretraining data, post-training, tokenizer, quantization, and runtime implementation. It cannot isolate the causal effect of architecture. Doing that would require much tighter training and compute controls. Our practical question is which complete model package works best here.

A selection rule that serves the actual goal

  1. Set a reliability floor. Define acceptable missed issues, false positives, unsupported claims, and handling of insufficient evidence for each task family.
  2. Exclude candidates that miss it. A very small model does not win by giving fast, unreliable advice.
  3. Compare the remaining resource costs. Record peak memory at the intended context, median and p95 complete-answer latency, and the human correction burden.
  4. Choose according to the limiting resource. If RAM is the problem, prioritize memory. If waiting is the problem, prioritize correct-answer latency. Keep both measurements visible.

For a 4090, my default is to start with the small dense student because it leaves more room for training activations. On the 64 GB Mac, add GPT-OSS-20B to the comparison sooner because there is more capacity for a sparse model’s stored experts. These are starting choices, not new hardware benchmarks.

GPT-OSS adds a useful third option. The relevant local candidate is gpt-oss-20b. OpenAI publishes it as roughly 21B total parameters with 3.6B active, with configurable reasoning effort and a 131,072-token context window. It is an open-weight, fine-tunable model under Apache 2.0. Its advertised context describes model support, not an affordable training sequence on these machines. Official model reference.

The larger gpt-oss-120b has roughly 117B total parameters and 5.1B active. Its sparse execution does not make its entire weight collection a 5.1B download or memory allocation. For this project it is a possible external teacher if suitable hardware is available, rather than the default local training student. 120B model reference.

What its architecture changes

Like Laguna, GPT-OSS uses a router and expert feed-forward networks. A token uses a subset of the experts, while ordinary attention and other shared operations still execute. The inspected native MLX implementation also combines full and sliding-window attention, grouped-query attention, rotary position handling, and learned attention sinks. Those sinks are extra terms in attention normalization; they are not stored cybersecurity facts. The implementation uses a specialized gated feed-forward operation. A derivative must preserve these details or deliberately retrain the change.

Compared with the dense Qwen example, sparse execution offers more stored capacity for a given active computation budget, at the cost of expert storage and routing complexity. Compared with Laguna, the published total and active counts differ, as do attention and expert layouts. An expert in one model has no automatic counterpart in the other. Matching router indices across families would not transfer a shared concept.

Harmony is part of the model contract

GPT-OSS uses Harmony to represent message roles, channels, answer endings, and tool handoffs. Distilled answer text can come from Laguna or Qwen, but it must be rendered into the student’s own format. A generic chat wrapper that happens to display an answer is insufficient evidence that training and inference agree. Harmony format guide.

For our first defensive specialist, reviewed final answers and concise evidence-based explanations are adequate training targets to test. Copying another model’s raw reasoning transcript is not required. If a later task includes tool interactions, the serializer and runtime must preserve the appropriate conversation state across those interactions. OpenAI’s verification guidance specifically separates compatibility smoke tests from fuller correctness evaluation. Implementation verification.

A Minitron-style GPT-OSS derivative

The research sequence is the same general idea: measure importance on representative data, physically reduce compatible structure, then recover useful behavior through training. Removing stored experts reduces the available expert bank. Keeping the number selected per token unchanged leaves much of the active expert computation intact. Lowering the number selected per token reduces computation but does not by itself remove weight storage. Depth or coordinated width reduction can affect both.

This does not amount to selecting “non-cyber experts.” Important behavior can be distributed across experts, and rare defensive cases may depend on infrequently used paths. A proposed 8B GPT-OSS derivative needs a tensor budget, compatible attention and routing dimensions, supported kernels, and recovery results. We have not implemented or validated that derivative. Starting with an existing small student is the earlier way to establish whether the desired quality fits in that size.

The hardware and implementation catch

The official Transformers inference guide gives an approximately 16 GB MXFP4 inference requirement for 20B and describes its optimized MXFP4 path for Hopper or later hardware. A 4090 is Ada; that particular path must not be assumed to work identically there. Other runtimes or converted formats may work, but need separate checks. The same guide estimates about 48 GB when using BF16. Transformers inference guidance.

The published Transformers fine-tuning example targets an 80 GB H100 and explicitly dequantizes the base to BF16. Its LoRA example also targets selected expert projections, beyond ordinary attention modules. That recipe is evidence that adaptation is supported, not evidence that it fits a 24 GB card unchanged. A memory-efficient local adapter route needs a supported quantized frozen base and measured activation memory. Official fine-tuning example.

Midnight’s pinned MLX dependency has GPT-OSS model and Harmony support. Its query/value modules fit the current adapter targeting pattern, but we have not demonstrated GPT-OSS training, correct target serialization, saving, and reload in this workflow. The raw packed-weight loading path can expand experts to BF16; a validated MLX conversion is therefore the sensible candidate for a compact Mac trial. MXFP4 and affine four-bit quantization are distinct formats, and their storage and numerical behavior must be recorded separately.

My recommendation

Benchmark GPT-OSS-20B as an alternative to the small dense student before investing in its pruning. If it gives substantially better task reliability at acceptable memory and latency, specialize it at the same size, then investigate whether it can be compressed. If Qwen already passes the same quality floor with lower relevant cost, ship that smaller student first.

“Cyber only” is best treated as a product objective: the assistant reliably handles a stated set of defensive tasks within a memory and latency budget. It should not mean that every non-cybersecurity capability has been proven absent. No practical pruning method provides that guarantee.

A useful security assistant still needs ordinary reading, code comprehension, dates, arithmetic, uncertainty, and the ability to distinguish claims from evidence. It may need to interpret a vendor advisory written in another language or recognize that a hostname and a command-line flag are different objects. Removing apparently unrelated ability can harm the task indirectly.

Define the job before shrinking the model

A first specialization could cover four families: reviewing configurations against supplied policy, interpreting incident evidence, reviewing secure code and proposed repairs, and answering questions from approved documents. Each family should have a clear expected output and explicit examples of insufficient evidence. A case containing a security-related term is not automatically a case that requires action.

For example, “Is this account activity suspicious?” is underspecified without expected behavior, identity context, and relevant timestamps. A good model should identify what is missing. Teaching it to confidently label every ambiguous case as an incident would inflate apparent helpfulness while creating operational noise.

A staged experiment toward a leaner model

  1. Establish the original baseline. Evaluate the exact quantized Laguna checkpoint on representative cases, including clean cases and difficult uncertainty judgments.
  2. Test an existing smaller student. Use the same evidence and task evaluation with dense Qwen, then benchmark GPT-OSS-20B as the sparse alternative. Establish the attainable memory/quality tradeoff before structural engineering.
  3. Use same-size specialization to test the data. Where training is supported, an adapter can reveal whether reviewed targets improve the chosen base. This is a useful intermediate result, but memory reduction still requires compression or a smaller student.
  4. Try modest structural reduction. Build a compatible Laguna derivative, profile it, then recover and evaluate it. A nearer intermediate size can expose problems before attempting an 8B endpoint.
  5. Advance only when the recovered model earns the reduction. Keep the best measured point; do not force 8B if a larger derivative has substantially better reliability.

This staging is an experimental recommendation, not a claim that a particular schedule or compression ratio will work. It separates the benefit of the data from the damage caused by architecture changes. A 33B-to-8B campaign that changes data, routing, depth, precision, and output formatting simultaneously would be difficult to diagnose.

Account for deployment support

The presence of a pruning framework does not imply that it imports every model. As checked for this guide, Laguna is documented in NeMo AutoModel’s fine-tuning coverage, while it was not listed in the inspected Megatron Bridge supported-family table. Those are different products and capabilities. A working full-SFT path is not proof that a Minitron pruning and distillation conversion is ready. AutoModel Laguna coverage; Bridge coverage.

For Midnight, any new derivative needs a configuration and tensor format that its native loader can understand. The generation path must preserve tokenization, end-of-answer behavior, and attention/cache semantics. A model that trains but cannot be reloaded faithfully is not a finished deliverable.

The training set does not have to contain only Laguna’s original answers. You can combine reviewed teacher outputs with human-authored explanations, documented policies, owned code, verified repairs, and other appropriately usable sources. What matters is that the target answer is supported and that the model is trained on the task you want it to perform.

Retrieval keeps a maintained external collection and inserts relevant material into the model’s input. Adding or correcting a document can affect the next answer without another weight update. It does not eliminate hallucinations: retrieval may miss the right source, and the model may misunderstand a retrieved passage. Retrieval-augmented generation.

Teach the model to use evidence

Suppose a vendor changes a recommended configuration. Update the source document, retain its version and date, and construct questions whose answers require that evidence. A reviewed example should show why the relevant passage applies, rather than merely asking the model to memorize a new number.

Training can include useful documents, irrelevant distractors, and cases where no supplied document answers the question. This teaches source selection and justified uncertainty. RAFT is a research example of training document-grounded answering in the presence of distractors; its results are not a certification for cybersecurity use. RAFT paper.

Use stronger supervision when the teacher is wrong

If an expert correction or a verified test outcome contradicts a teacher answer, do not retain the teacher’s answer solely because it came from the larger model. Resolve the evidence and make the reviewed target authoritative for that task. Combining teachers can increase coverage, but agreement among models is not independent proof: they may share training data or the same misconception.

For a legitimate code-review case, a useful outcome might include a corrected implementation and tests that verify the intended security property without operational exploitation. The model should learn to explain the repair, the assumptions it depends on, and what the test does or does not establish.

New facts do not make the weights grow indefinitely

A fixed adapter keeps a fixed number of parameters while its values change. Its training archive and retrieval library grow as examples and documents accumulate. Those are separate disk budgets. There is no reliable rule that one gigabyte of documents becomes a certain number of megabytes of learned weights.

Use retrieval for changing facts and fine-tuning for repeatedly useful patterns. Both can teach or supply factual information, but they differ in how easily an answer can be traced to a source, corrected, or removed. Keep provenance even when information is incorporated into training.

There is no single file called “the cyber dataset” that solves this project. We need several collections, each with a different role. A small collection can reveal implementation problems; it cannot establish that a model retained broad expertise after a major structural change.

A manageable starting allocation

For specialization, start with 500–2,000 independently reviewed scenarios. As an initial planning choice, allocate 30% to configuration review, 25% to incident evidence, 25% to secure coding and remediation, and 20% to document-grounded questions. Adjust from real workload evidence. These counts and percentages are not known sufficiency thresholds.

Include clean configurations, expected administrative activity, ambiguous evidence, and incomplete context throughout the task families. Keep task type separate from outcome label. “Incident evidence” does not mean the correct answer must always be “incident confirmed.” Sample the difficult distinctions that a working analyst actually needs.

Suitable source families

  • Secure-development requirements: use versioned NIST SSDF practices and OWASP ASVS requirements to ground review scenarios.
  • Current vulnerability prioritization: use dated vendor advisories and the CISA KEV catalog. Catalog inclusion alone does not prove that a particular installed system is affected or compromised.
  • Your own work: use appropriately de-identified configurations, owned or licensed code, reviewed incident records, policy documents, and verified corrective outcomes.
  • Authored scenarios: create realistic defensive cases with explicit expected results, then independently check that the facts support the answer.

Public availability is not the same as permission to redistribute or train. Preserve the source’s applicable terms and the exact checkpoint’s license. Do not silently mix the predecessor Laguna XS.2’s terms with XS 2.1’s current card. Model identifiers, versions, and source permissions belong in the dataset manifest. This guide is a technical plan, not a legal determination about a particular collection.

What each record should preserve

Keep the source and revision, date, scenario family, task, prompt, relevant evidence spans, expected decision, reviewed response, version and policy assumptions, synthetic-data status, and review outcome. For generated targets, also record the teacher checkpoint, quantization, template, generation settings, and raw answer. A corrected label with an incorrect explanation is not an accepted training record.

Split before multiplying examples

Assign source families to train, development, and test before making paraphrases. If two cases come from the same incident, repository, advisory, or template family, keep related versions together. Otherwise a model can appear to generalize by recalling nearly identical material. Deduplicate exact and near copies. Add a time-based holdout for changing advisories. Research on deduplication and evaluation contamination.

Expand toward 5,000–20,000 reviewed cases only when fresh evaluation identifies coverage gaps. For major pruning recovery, plan in processed tokens and compute, not only case counts. A thousand carefully reviewed cases and a hundred billion recovery tokens are different investments.

The evaluation should answer two questions: did the model become better at the intended work, and did the chosen compression actually improve deployment? A single aggregate score cannot answer both. Freeze the rubric before choosing the final checkpoint.

Count malformed outputs, truncation, and generation failures in the denominators. Excluding them makes a brittle model look better. Report both false positives and missed issues; which matters more depends on the actual workflow. Show per-task results so an improvement in one easy category does not hide a regression in another.

Use independent evidence

Compare the unchanged student, trained student, and teacher on the same unseen scenarios. Human or model-assisted grading should use a written rubric and source evidence. A second model’s preference is useful triage, but not a replacement for expert review of important decisions. Avoid letting the teacher serve as the sole author, sole trainer, and sole judge of its own examples.

Twenty held-out cases can expose obvious errors but produce very coarse scores: each answer changes the rate by five percentage points. For a serious quality claim, use substantially more independently constructed cases and report uncertainty. Repeatedly inspecting the test set to decide new training changes turns it into development material.

Measure actual efficiency

Record weight bytes, process memory, accelerator allocation, prompt-processing time, first-visible-answer time, complete-answer time, and failed requests. Keep input content, output requirements, and generation limits comparable. Warm up the runtime and repeat timings. Shorter incorrect answers do not count as an efficiency success.

For MoE, report total and active parameters separately. For quantization, identify the format and which tensors remain higher precision. For distillation, include teacher-generation time in training cost but exclude the teacher from deployed-student memory when it is not used at inference.

Define a useful promotion rule

As an example design, require no material regression in evidence fidelity or important remediation checks, fewer unnecessary refusals on legitimate cases, and a measured memory or latency benefit for the compressed candidate. Set the acceptable margins from the workflow before examining the final test. This is a proposed evaluation policy, not a claim that the current model passes it.

Retain the previous model and all exact preprocessing and export metadata. Reload the candidate in the real application and verify that it produces the intended behavior. Training-time success is incomplete until the saved model works faithfully in its deployment runtime.

Yes, a distilled student can end up refusing less than its teacher or its starting checkpoint. That is a possible learned outcome, not a guaranteed effect of distillation. A student may also preserve refusals or acquire them from its teacher. The teacher itself is not changed merely by providing training targets.

Refusal behavior depends on learned weights, the prompt and conversation, and sometimes separate application rules or filters. A checkpoint update affects only part of that system. It is not a reliable “delete every refusal” switch, and there is no corresponding chunk of storage that becomes free when refusal frequency decreases.

Distinguish willingness, knowledge, and correctness

A model can know relevant technical material but decline a request. It can also answer confidently without knowing enough. Reducing refusal frequency does not establish better expertise, stronger reasoning, or more accurate remediation. These are separate properties and should be measured separately.

Fine-tuning research has shown that safety behavior can degrade even when that degradation was not the intended purpose of customization. That makes refusal behavior a useful evaluation dimension in a specialization project, rather than something to assume will remain unchanged. Research on safety changes after fine-tuning.

The useful target for this project

For legitimate cybersecurity use, measure unnecessary refusal on clearly defensive tasks: interpreting supplied logs, reviewing a proposed fix, explaining a configuration requirement, or comparing evidence against an approved policy. Measure the retained boundary on genuinely harmful requests separately. Do not combine those categories into one “refusal rate” and optimize it downward indiscriminately.

XSTest is a research example of studying exaggerated safety behavior through benign prompts and contrasting unsafe prompts. Its general lesson is that an assistant should distinguish the actual request from alarming vocabulary. It is not a cybersecurity-specific quality certification. XSTest.

What the published guide does and does not claim

This project has not established a model with universally removed refusals. Minitron pruning, domain specialization, CODI, and refusal behavior are different axes. Compressing a network does not predict exactly how any of them will change. The intended outcome is a model that answers legitimate requests well and expresses uncertainty when evidence is missing.

The practical check is therefore paired: improved helpfulness on legitimate work, alongside factual accuracy, useful limits, and retained safeguards. A model that always produces an answer can still be much less useful than one that correctly identifies missing information.

The working Mac is an M5 Max with 64 GB unified memory. The alternative setup has a single RTX 4090 with 24 GB VRAM and 128 GB host RAM. Unified memory is shared with macOS and other applications. On the PC, host RAM and GPU VRAM are separate resources; offloading can move data between them, but transfer costs and training support matter. Apple specifications; NVIDIA specifications.

Which settings move the limit?

Longer examples, larger microbatches, more adapted layers, wider adapters, teacher passes, and retained hidden states can all increase memory. Activation checkpointing reduces retained activation storage by recomputing work. Gradient accumulation can increase the effective batch without keeping every example’s activations resident simultaneously; it does not remove model weights. MLX LoRA memory guidance.

The current Midnight trainer uses batch one and, in the verified pilot, rank-16 adapters on query/value projections in the final eight layers with up to 1,024 tokens. It has no activation checkpointing or CPU offload. A Linux/CUDA build path exists, but this training workflow has only been verified on Metal. Its current CUDA allocator policy also caps allocations at 20 GiB; that is software policy, not an intrinsic 4090 limit.

For GPT-OSS, the ideal four-bit arithmetic is not the actual MXFP4 checkpoint or peak-memory size. Keep quantization scales, higher-precision tensors, cache, workspace, and training state in the budget. GPT-OSS-120B’s ideal four-bit weights alone leave too little headroom for a sensible 64 GB Mac training plan, and exceed 4090 VRAM. The PC’s 128 GB host RAM may support some inference offloading arrangements, but it does not make 120B a practical default training student. See the GPT-OSS hardware details.

Full training is a separate scale

Conventional Adam-style full training may need roughly 16–18 bytes per parameter before activations, depending on precision and state storage. A 1B model can therefore need about 16–18 GB before workspace; 3B about 48–54 GB. Optimizer compression and offload change the calculation. For a from-scratch local experiment, 100–500M is a sensible starting range; 1–2B on the Mac is a demanding memory target, and around 3B is an edge experiment rather than a verified ceiling. Training it enough to become useful remains the larger commitment. Training-memory anatomy.

Separate five costs: preparing and reviewing data, generating teacher targets, running student updates, evaluating candidates, and implementing missing architecture support. The first and last can dominate calendar time even when the training kernel is fast.

Count processed tokens consistently

If 10,000 examples average 1,000 total input-and-answer tokens and training makes three passes through them, that is approximately 30 million processed sequence tokens. If loss is applied only to the assistant’s answer, the supervised-token count is lower, but the prompt still incurs model computation. Report both quantities rather than using the smaller denominator to suggest a much larger training throughput.

Training duration ≈ processed sequence tokens ÷ measured sequence tokens per second

Teacher generation and review

Ten thousand 500-token teacher answers contain five million output tokens. At an effective 100 output tokens per second, generation alone takes about 13.9 hours; at 25 per second, about 55.6 hours. Prompt processing, model loading, and review must be included in the measured rate or added separately. Offline sequence distillation lets this stage run independently of student training.

If reviewing a scenario takes three minutes, 1,000 scenarios consume 50 reviewer-hours. Complex code or incident cases can take much longer. Automated checks and model-assisted review help prioritize work, but their own error rate must be assessed. Do not call a model-assisted review independent expert validation.

Why industrial Minitron is a different project

For scale, 94 billion processed tokens at a hypothetical sustained 1,000 tokens per second take about 2.98 years, before additional teacher work and overhead. This is arithmetic, not a prediction of local performance. It explains why published Minitron recovery runs use large compute clusters and why a narrow specialization experiment is a more realistic local starting point. Published recovery budgets.

Laguna need not require the exact same token budget as those papers, but a much smaller budget must demonstrate its own quality. The correct statement is “we will test how much recovery is needed,” not “a few thousand examples are equivalent to the published method.”

Calendar expectations

A small existing-student experiment can be organized around short measured training runs once its data is ready. Building a serious reviewed corpus, comparing several candidates, and checking failures is a multi-day or multi-week effort. A new Laguna pruning converter and recovery system is research engineering with an uncertain schedule. Set bounded milestones and stop conditions instead of promising a finished 8B specialist by a date unsupported by measurements.

Ordinary inference does not update model weights. A conversation can provide temporary context, and a retrieval library can store durable information, but neither action is automatically a gradient update. Continual learning requires an explicit collection, review, training, and deployment process.

  1. Work and captureSave a useful source or a corrected example with its evidence and version.
  2. Train a candidateUse approved new material together with selected older examples.
  3. Evaluate and promoteCompare against the current model, then change versions between conversations.

Two queues with different turnaround

A knowledge queue can update the retrieval library after its sources are checked. A training queue can collect reviewed prompt/answer pairs and verified outcomes. Facts that need to be current should not wait for the next adapter update merely because model training is available.

The training queue should not treat every model response, log line, or retrieved document as an instruction to learn. A user correction is valuable, but it still needs enough evidence to be a reliable target. Keep failed suggestions and their corrections linked so the review process can distinguish what happened from what should be taught.

Concurrent use and training

It is possible to serve an immutable model version while a separate candidate trains. A system can sometimes share frozen base weights and keep different adapters, but that requires a deliberate implementation. Independent processes may duplicate weights. Both workloads still need their own attention/work state and compete for computation.

On the Mac, those jobs share the same unified-memory budget. A 33B adapter-training estimate does not guarantee enough headroom for simultaneous serving with long conversations. For responsive use, schedule training during idle periods or use the other machine for training. Keep the running conversation on one stable version; switch after the candidate passes evaluation and the conversation reaches a clean boundary.

Do not forget yesterday’s skills

Successive fine-tuning can degrade older capabilities. Keep a representative replay set and retention tests, and compare new behavior against the current model. A smaller update and a carefully chosen data mixture may help, but there is no universal safe learning rate or replay percentage. Continual fine-tuning and catastrophic forgetting.

For an evolving cybersecurity assistant, retain cases from older software versions when they remain relevant, but mark those versions explicitly. The objective is to distinguish contexts rather than overwrite an old fact with an apparently universal new answer.

What Midnight currently supports

The existing experiment supports reviewed batch targets, training, evaluation, immutable adapter checkpoints, and export verification. It does not yet provide automatic feedback capture, a retrieval knowledge store, or a new-data continual-training workflow. Its current resume operation is an exact continuation of the same data and settings; adding a corpus is not merely resuming that run.

A future warm-start mode could initialize a candidate from an existing adapter while intentionally resetting or migrating training state for the new corpus. That mode needs its own metadata and tests. Until then, a new versioned run on the cumulative approved corpus is a clearer contract than silently changing the data beneath a checkpoint.

CODI means Continuous Chain-of-Thought via Self-Distillation. It trains a model on an explicit-reasoning task and a latent-reasoning task, using shared model weights. Instead of generating every intermediate reasoning word, the latent path feeds internal vectors through additional computation steps before producing an answer.

The published method uses adapter training and representation alignment. Its reported compression concerns reasoning steps, not a reduction from 33B weights to 8B. A CODI-adapted Laguna would still retain roughly its chosen base size plus learned additions, and its latent steps would still consume computation. CODI paper; official implementation.

Why ordinary training support is not enough

A text-only supervised trainer normally maps input token IDs to output-token loss. CODI also needs a path for embedding inputs, access to selected hidden states, a learned projector where used, a differentiable latent loop, and the appropriate combined losses. Cache positions and gradients through latent inputs must remain correct. These are additional model and training interfaces, not a switch that hides the printed reasoning.

Weight sharing avoids a mandatory second full base copy. It does not remove the extra teacher passes, latent steps, activation history, and loss computations. Therefore the earlier model-size estimates for short adapter training are not established CODI limits.

What the local latent experiment found

A separate 0.5B CODI-style experiment was trained and remains paused. Its latent path answered 36 of 256 new development questions correctly, or 14.1%. The same trained weights answered 220 of 256 correctly with explicit reasoning, or 85.9%. An experimental native inference implementation matched four reference prompts; native training remains unfinished.

Those findings show that the mechanism can be implemented, but the tested recipe lost too much accuracy to ship. They do not prove that all latent methods fail. The sensible continuation is the incomplete controlled comparison already recorded, followed by a useful quality/latency result before attempting large-model integration.

What “from scratch” changes

You can instantiate a smaller transformer or compatible Laguna-shaped architecture with random weights. It then has no inherited language or code knowledge. Distillation targets can supply supervision, but the model must learn its foundations as well as the task. An 8B random student is not comparable in cost to adapting an already trained 8B checkpoint.

A historical compute-efficient scaling guideline places training data on the order of 20 tokens per parameter. That suggests roughly 20B tokens for a 1B model as a scale reference, not a minimum requirement or a guarantee of capability. Different data, tasks, and inference-cost objectives can favor different ratios. Chinchilla scaling research.

For local architecture research, a 100–500M from-scratch model is a meaningful experiment. For a useful cybersecurity assistant, inherited weights offer a much more economical foundation. CODI can be studied separately once the ordinary answering baseline is reliable.

Quality results were mixed

Development verdict accuracy moved from 12/20 to 15/20. Test verdict accuracy moved from 15/20 to 16/20, while false positives on seven clean test cases increased from 1/7 to 2/7. All 20 outputs in each evaluated set were valid JSON, but targeted semantic review still found important recommendation defects.

The best development loss was reached well before the last update; continuing the small run did not keep improving it. This is a useful illustration of why training duration, valid formatting, and lower training loss should not be treated as model quality. The experiment needs broader, independent evaluation before any claim of general cybersecurity expertise.

Engineering checks that did pass

The pipeline validates corpus boundaries and provenance, saves optimizer and adapter state, verifies resumed training in a controlled comparison, and checks freshly reloaded outputs. The exported adapter also ran in Midnight’s server. These checks reduce the chance that an apparent training gain disappears because of broken serialization or export.

They do not replace task evaluation. The public measurement summary includes the relevant values and limitations without machine paths or private raw cases. The separate latent experiment’s poor generalization is also recorded there, so the ordinary distillation success is not confused with CODI success.

What remains unverified

We have not demonstrated Laguna structural pruning, an 8B Laguna derivative, same-sized Laguna adapter training, GPT-OSS adapter training or pruning, a matched three-model comparison, CUDA training of this pipeline, general cybersecurity reliability, a production retrieval system, or automatic continual learning. Those are future experiments and implementation work, not features implied by the successful 4B pilot.

What to choose first

For the stated goal of a leaner cyber model, start with the demonstrated Qwen 4B pipeline and a serious held-out evaluation. Compare an 8B student if 4B misses the quality floor, and GPT-OSS-20B if sparse execution or stronger task performance may justify its larger stored base. Keep Laguna as a teacher and reference. Same-size Laguna adaptation remains useful for testing data quality or preserving a proven capability advantage; it is not by itself completion of the memory-reduction goal.

A useful initial evaluation budget is approximately 200 independently reviewed cases across the chosen task families, including substantial clean and insufficient-evidence subsets. This is a planning starting point, not a statistical guarantee. Use separate development and final-test families, and expand the fresh evaluation when gains are small or high-impact failure modes remain uncertain. Compare each trained model with its own unchanged baseline.

For pruning, prefer an initial reduction small enough to diagnose. The exact intermediate size should follow a tensor audit, measured candidate importance, and compatible runtime dimensions. A path toward 8B can remain a long-term research objective without pretending the endpoint is guaranteed.

The artifact we should be able to hand over

A finished model package needs its exact base identity, tokenizer, chat template, quantization description, adapter or merged weights, configuration, applicable notices, and versioned evaluation report. If architecture changes, include the loader and runtime contract. If CODI is used, retain the learned additions and latent execution loop; merging ordinary adapters does not remove that loop.

Record quality alongside deployment cost. “8B,” “four-bit,” or “distilled” is a description of the artifact, not proof that it is useful. A larger model that handles uncertainty correctly may be preferable to a smaller model that generates fast but unsupported conclusions.

Questions the next experiment must answer

  • Can reviewed domain data improve the tasks at fixed architecture?
  • How much of the gap is better solved by retrieval than by weight updates?
  • Which model offers the best correct-answer latency and memory use on the actual machine?
  • Does a pruned Laguna recover enough capability within a feasible training budget?
  • Can the saved model be reloaded, evaluated, and rolled back predictably?

Completion means a reloadable model that passes the agreed cybersecurity evaluation and demonstrates a stated memory or latency improvement against the existing deployment. Measure short and long cases, cold and warm starts, failed and truncated outputs, peak application memory, and median/p95 complete-answer time. Include retrieved-context and human correction costs. “More specialized” and “leaner” should each have evidence.

No separate project is required to begin

Midnight already contains a working distillation and adapter-training prototype under its experiments area. We can use that for the next bounded comparison. For a sustained program involving datasets, pruning, recovery, and multiple hardware backends, I recommend a separate training repository with an explicit export contract to Midnight.

This is a recommendation about software organization. It does not require a second Mac, a separate model architecture, a new user interface, or abandoning the native Swift/MLX work. A separate Codex task is also different from a separate repository: neither is a prerequisite for distillation. This guide does not create or migrate a project.

Why separate sustained pruning work?

Pruning can change tensor shapes, layer counts, attention layouts, routing, or quantization assumptions. It often needs different dependencies from an inference application. Keeping recovery jobs and experimental checkpoints outside the app makes it easier to reproduce training runs, pin CUDA or MLX versions, and avoid tying app releases to a training campaign. It also gives datasets and private examples their own access and retention rules.

A separate repository does not automatically make NVIDIA pruning tools support Laguna or make CUDA training work on a Mac. Those are implementation questions. Native MLX adapter work can remain native. If a particular recovery method requires PyTorch or NVIDIA tooling, its training environment can be isolated while Midnight continues consuming a verified export.

Keep one implementation of shared model behavior

Avoid copying tokenizers, chat serializers, and model implementations into two diverging codebases. Pin a common library or extract a small shared package when needed. The training project and Midnight must agree on the model’s actual inference behavior. For GPT-OSS, that includes Harmony and attention semantics; for a pruned Laguna, it includes the modified configuration and expert layout.

An ordinary adapter for an already supported base may need no new model implementation in Midnight. A structurally new derivative may require a loader or kernel change there. Those application changes should be driven by a concrete exported candidate and compatibility checks. A separate training project keeps the boundary clear; it does not remove the boundary work.

A sensible transition

  1. Finish a small baseline comparison in the existing prototype. Reuse the known working path while clarifying the task rubric and export requirements.
  2. Separate when the work expands. Move reusable training orchestration and evaluation into the training repository; retain compatibility tests and inference integration in Midnight.
  3. Version the handoff. Export the base reference plus adapter, or complete derived weights, with tokenizer/template, configuration, precision details, provenance manifest, and measured results.
  4. Promote deliberately. Load the candidate in Midnight, reproduce the required evaluation, and keep the previous model available for rollback.

Raw datasets, private incidents, and large weight files should live in suitable data or artifact storage rather than ordinary Git history. A training code repository can contain schemas, manifests, small permitted fixtures, run definitions, and evaluation code. Keeping the repository separate does not mean it needs to be public.
